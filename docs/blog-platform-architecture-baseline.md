## Existing routing configuration

`netlify.toml` currently declares:

- **Build**: `npm run build`, `NODE_VERSION = 22`, `SECRETS_SCAN_OMIT_KEYS = INDEXNOW_KEY`.
- **Plugin**: `@netlify/plugin-nextjs`. `publish` is deliberately unset — the adapter resolves it.
- **Contexts**: production pins `NEXT_PUBLIC_SITE_URL = https://asteriastar.com`; deploy-preview and
  branch-deploy override the build command to use `$DEPLOY_PRIME_URL`, so a preview can never emit a
  production canonical.
- **Headers**: `Strict-Transport-Security: max-age=63072000` and `Access-Control-Allow-Origin: *` on
  `/*`; `X-Robots-Tag: noindex, nofollow` on every non-production context.
- **Redirects**: two — `www` → apex, 308, `force = true`, for both schemes. **Nothing else.**
  `/blog` is entirely unclaimed.

### A gotcha already recorded in this repository, and why it matters here

`netlify.toml` carries a warning written during the migration:

> A `[[headers]]` rule with `Netlify-Vary = "query"` for `/api/*` was tried first and verified NOT to
> work: netlify.toml header rules apply to files in the publish directory, not to responses produced
> by the Next.js server function.

That is about **headers**. Redirects are a different engine and are documented to behave differently
(see the ADR), but the lesson stands and is adopted: *confirm on a real deploy rather than trusting
the build log.*

## `/blog` is free

- No `src/app/blog` directory exists.
- `/blog` appears in neither `src/lib/routes.ts` nor `src/app/sitemap.ts`.
- `https://asteriastar.com/blog` returns **404** in production today.

There is nothing to migrate, redirect, or preserve.

## Surfaces the blog has to match

**HELPERG ecosystem bar** — `src/components/ecosystem/{EcosystemBar,EcosystemDisclosure,EcosystemLinks}.tsx`
(289 lines) over `src/lib/ecosystem/projects.ts` (227 lines). The registry is **deliberately
dependency-free**: it has no imports at all, and `scripts/validate-ecosystem.ts` enforces that,
because it ships to the browser. That makes it copyable verbatim into a second repository, which is
the sync strategy the ADR adopts.

**Global search** — a prebuilt static index at `public/search-index/{manifest,core,catalogue}.json`,
7,761 documents in 2 shards with per-shard checksums, generated by `scripts/build-search-index.ts`
and gated by `scripts/validate-search-index.ts`. It is a *static artefact fetched at runtime*, which
is exactly the shape a second publisher can add to without rebuilding the first.

**Analytics** — WebmasterID, loaded once in the root layout through `next/script`
(`afterInteractive`), site id `wm_knpkrkxcizuzoa0s`, all identifiers public. No consent gate exists
on this platform.

**robots / sitemap** — `src/app/robots.ts` allows everything except `/app/` and `/api/`, and names a
single sitemap, `https://asteriastar.com/sitemap.xml`. `src/app/sitemap.ts` is 1,024 lines and
enumerates ~8,700 URLs from the data layer.

**IndexNow** — key `c292fa58c74f45f9ad982e152b4f7c1c`, served at
`public/c292fa58c74f45f9ad982e152b4f7c1c.txt`. `INDEXNOW_KEY` is a Netlify environment variable
scoped to the production context only, so a preview cannot notify a search engine. Submission runs
through `scripts/indexnow-submit.ts` and `src/app/api/indexnow/route.ts`, plus a
`.github/workflows/indexnow.yml`.

**CI** — `.github/workflows/ci.yml` runs the repository's own gates on every PR and every push to
main, on Node 22, deliberately host-independent.

## What this baseline establishes for the blog

1. The main site is a Next.js **server-function** site, not a purely static one. Any routing
   mechanism must be one that runs *before* that function.
2. `netlify.toml` redirects are the only routing layer the main site currently uses, and it uses two
   trivial rules. Adding one prefix rule is a small, reviewable change.
3. Both projects will live on the same Netlify team, which the proxy documentation requires.
4. The ecosystem registry and the search index are both already shaped for reuse across a repository
   boundary — neither needs redesigning to support a second publisher.
5. `/blog` is unclaimed, so there is no collision to resolve and no legacy URL to preserve.
